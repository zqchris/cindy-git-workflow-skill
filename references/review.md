# 评审处置

目标是解决有证据的实质缺陷，同时保留用户确认的功能。review、CI 和机器通知都不是新的产品需求或资源授权。

## 一轮如何完成

1. 读取当前 PR 的完整评论、inline threads、checks、mergeability 与 head；回到原需求和验收，不只按最新摘要行动。
2. 用当前代码、调用者、数据流或复现证据判断每条意见，先判断再改码。不为理解每条评论先启动测试版。
3. 采纳的实质问题按根因合批修复，maker 自审完整 diff，做直接相关回归。实际运行与证据复用按 [验收规则](runtime-acceptance.md)；停止要求始终有效。
4. 在授权内合批 commit/push。对接受和拒绝的意见分别回复结论、关键证据和实际动作；修好或说明不采纳理由后才 Resolve 并回读。真实风险接受但延期不等于修好，不借 Resolve 隐藏未解决问题。
5. 核对最新 head 的检查与讨论状态，在原任务报告本轮增量和下一步。不转发到其他会话，不另建 reviewer 或协调员。

## 三类判断

**采纳**：目标内存在真实功能错误、兼容回归、权限/数据风险或实际 CI 阻断；证据能说明触发路径与影响，修复保留原目标。确定的代码路径/协议冲突已经可以成立，不要求先制造生产事故。

**有据拒绝**：风格偏好、无实际消费者的兼容需求、不可达前提、无实质收益的非阻塞建议、范围外重构或未授权产品改向。说明不成立的前提、已有保障或与目标的冲突。有据拒绝就是完成处置，不需要用户逐条许可，也不需要造提交。

**需决定或外部解除**：已确认缺陷无法在当前权限和产品约定内解决，或真实门禁阻断。说明具体影响和最小选择，完成其他独立工作；不无止境尝试，也不假称修复。

## 保留产品，避免循环

- 建议方案会删功能、降低覆盖、禁用入口或削弱安全时拒绝方案；底层缺陷若成立，仍须另找满足原功能的修复。不能只说“产品意见不采纳”就漏修真实安全问题。
- 同一语义跨入口时核对完整受影响消费者，不从 changed files 倒推范围。原需求遗漏不能一律推成“后续再做”。真正独立目标先说明，不自行开 issue、session 或叠 PR。
- 无新证据的重复意见沿原结论收口，不空提交触发重审。新复现、调用者、相关代码或门禁变化才重评；P1 标签、换措辞或重复催促不算新证据。
- 多轮同根因问题先审视不变量和共同原因，但重构仍要证明收益。不设固定三轮停工、300 行禁发等配额；规模只帮助检查是否混入独立目标。
- CI 失败区分本次回归、已有基线问题与环境问题，引用日志和提交。无关既有故障不冒充本次修复，也不删除检查或放宽断言制造绿灯。
