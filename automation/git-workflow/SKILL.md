# Git Workflow（开发工作流全周期规范）

适用于**任何**仓库的通用开发工作流。需要 GitHub/GitLab 数据时优先用 `git` / `gh` / `glab` / GraphQL / 仓库脚本;不要依赖通用 GitHub plugin 的默认流程判断。

**仓库专属优先**:任何仓库的具体命令（建 worktree / 启动 / 验证方式）、PR 模板、Self-review 门槛、reviewer、发版与分支模型,一律以该仓库的 `AGENTS.md` / `CLAUDE.md` / PR template 为准。本 skill 只给跨仓库通用的原则和工程质量底线;进场先读仓库规范再干活。

**项目规则加载**:进场时检查 `~/.agents/skills/git-workflow/projects/` 下是否有匹配当前仓库名的 `.md` 文件（如 `xdt-maker.md`、`cli-slg.md`）。有则读取,作为该项目的验证命令、PR 模板、reviewer、特殊注意事项的参数来源。项目规则的优先级：仓库 `AGENTS.md` > 项目规则文件 > 本 skill 通用规则。

## 触发与硬门禁

**何时必须走本 skill:**

- 即将为当前任务修改现有仓库的 tracked/untracked 内容、Git 引用或发布状态——Edit/Write、删文件、commit、push、创建/更新 PR/MR——在**第一次写操作之前**加载。
- 只读任务后来转为实现时，在转折点加载并执行写前自检；此前不预加载。

**以下情况禁止触发本 skill:**

- 只读查看源码、`git status/log/diff/show/blame`、搜索历史、查询 PR/issue/CI、评估或解释仓库。
- 为安全审计或兼容性研究下载、解压或 `git clone` 第三方开源仓库，并保持其源码不变地阅读或运行。
- 把聊天、媒体、报告、数据集或其它非代码产物写到目标仓库之外；普通个人/家庭查询即使提到 GitHub、开源项目或 agent，也不触发。
- 仅讨论实现方案、推荐项目或比较 release；只有决定修改某个仓库时才触发。

**子代理资源门禁（强制）:**

- 本 skill **不构成创建子代理的授权**；只有用户或更高层指令明确允许时才能使用。
- 一个根任务从开始到结束累计最多创建 **10 个不同子代理**。这是累计上限，不是同时运行数；关闭子代理、context compaction、切换阶段或进入 review follow-up 都不会重置计数。
- 创建前先核对本根任务已创建数量。优先继续使用已有子代理；同一问题、同一文件范围或同一 review 视角不得重复新建。
- 只有「对抗式预审」的风险条件命中且已获得子代理授权时才用 1 个独立 reviewer；小改由主 session 自审。后续继续复用同一个，不得用大批子代理替代范围判断和实现计划。
- **子代理模型档位必须显式降档,禁止默认继承主会话主力模型**:机械活(读码/拉数据/统计)用 haiku 级,分析与 review 用 sonnet 级或订阅计费通道;主力模型只留给判断质量决定成败的环节并说明理由(详见 agent-ops skill)。
- 达到 10 个后立即停止继续创建。确需突破时，先向用户说明已用数量、继续原因和预计新增数量，取得明确同意；不能把“任务复杂”当作默认豁免。
- 每次压缩上下文或交接时，把“已创建子代理数 / 10”写入摘要，避免新上下文重新计数。

**写前门禁（强制执行，不是建议）:**

动手前执行（**先用宿主 `get_current_session_id` 取会话 id 并带上 `--session`**，否则分支归属冲突只能给 WARN、拦不住）:
```bash
bash ~/.agents/skills/git-workflow/scripts/preflight.sh --session <宿主会话id>
```

- 输出 `PASS` → 可以继续写操作
- 输出 `FAIL` → **立即停止**,按 ACTION 提示处理（通常是 `git-start.sh` 起 worktree）
- 输出 `WARN` → 确认是否当前任务的 WIP 后继续

**不执行 preflight 就开始写 = 违规。** 这不是可选步骤。

**`--session` 传的是宿主会话 id，不是 `CLAUDE_CODE_SESSION_ID`／agent 内部 sdkSessionId**——那是另一个 id 空间，形状同样是 UUID 所以肉眼分不出（hb-register 也踩过同一个坑）。检查5 用它比对总管 `tracked[]` 里登记的 owner：**分支属于别人而你要往上写，直接 FAIL**。2026-08-04 实踩：#1581 的 owner 是 `6340563b`，另一个会话 `a22fba91` 接了转交后往同一分支 push 了 3 个 commit、resolve 了 5 条线程、还把 PR 转成 draft；两人分别加了「失败就交还写入权」与「超时不回滚代际、保持单调」，同一段代际语义被两个相反取向叠在一起，谁接手都得重判一次。当时没有任何机制拦住它。

如果 preflight FAIL 后需要起 worktree:
```bash
bash ~/.agents/skills/git-workflow/scripts/git-start.sh <task-slug>
```

**例外**:用户明确说"就在当前分支改";或改动是当前 worktree 的 follow-up。

**已存在分支的 follow-up（review follow-up / 堆叠 PR）:**

不需要 git-start 新建 worktree，但必须在动手前确认本地状态对齐远端：
```bash
bash ~/.agents/skills/git-workflow/scripts/align-branch.sh <branch-name> [remote]
```
- 输出 `ALIGNED` → 可以开始改
- 输出 `BEHIND` → 需要 pull 后再改
- 输出 `DIVERGED` → 有冲突风险，先 fetch 对比再决定

多轮 follow-up 中 shell 工作目录可能被重置——所有 git/测试命令用**显式绝对路径**（`git -C <worktree>`），防止误把主 checkout 切到工作分支。

**堆叠 PR（stacked PRs）:**

多个 PR 有依赖关系（如 #482→#483→#484）时：
- 从**栈底**开始修（最底层的 PR 先改完、push、确认）
- 修完底层后逐层 merge 到上层分支再 push;沿链更新一律用 **merge，禁 rebase**（含更新到最新上游默认分支、解决冲突）
- 每个 PR 有自己的分支，不要在同一个分支上处理多个 PR 的改动;仅当改动文件在各分支内容一致时才可携带 checkout 分流提交
- 每层 push 后确认 GitHub PR head 已更新再处理下一层
- **开 PR 前**：先把整条链 merge 最新上游默认分支，全量验证绿了再推
- **跨 fork 堆叠**（上游无直接写权限、经 fork 推分支）：无法用前序分支做 base——全部 base 默认分支,每个 PR 描述顶部标注依赖序（#A → #B → #C）和净增量 compare 链接;前序合并后后续 diff 自动收敛,描述里提醒 reviewer 按序看
- 某个 worktree 正在服务运行中的 dev 实例时,把它固定在**栈顶完整分支**;修底层分支问题另起 checkout,否则热更新会丢文件（UI 组件凭空消失）

## 起步（新任务流程）

0. **进场读仓库规范 + 项目记忆**:`AGENTS.md` / `CLAUDE.md` / PR template + 搜 memory。
0.5. **按需决策考古**:变更既有产品行为、处理 issue/PR 或碰到历史争议时，按下方「决策考古」查清路线；机械配置/文档修正和无历史的新代码可跳过。
1. **最新上游干净基底**:`bash ~/.agents/skills/git-workflow/scripts/git-start.sh <task-slug>`。脚本必须先 fetch `upstream`（存在时）或 `origin`，再从该远端默认分支创建 worktree；禁止从本地 `main/master`、当前 HEAD 或未 fetch 的远端引用起分支。
2. **实现**:一个 PR 围绕一个完整产品目标；技术上相互依赖、拆开不可用的部分保留在同一 PR。每完成一个可独立理解的逻辑单元做一个有意义的 commit。
3. **质量门禁**:ready PR 按「Code Review 质量标准」逐项自查；draft 只做最低安全与可读性检查。
4. **安全扫描**:按「安全门禁」检查后才 commit。
5. **验证**:按影响范围选局部/相关链路/完整检查；一批改完后统一测，不在每个小修之间反复跑。
6. **整理 commit**:按「Commit 纪律」squash WIP，确保 `git log --oneline` 是干净叙事。
7. **交付**:默认实现 + 验证 + 汇报;用户要求才开 PR,开 PR 时按完成度选 draft/ready（见 Publish 的档位判定）。
8. **收口**(仅 ready PR):同一回合完成「发布自检 + 心跳登记 + 汇报带心跳行」三件套(见 Publish 收口清单)。bot 首批意见**不守等**——心跳 settle 门控会等全部 bot 出齐后合并成一条转交。

**需求澄清与意图契约（动手前,强制）:**

上下文不足时的正确动作是**讨论**,不是脑补猛干,也不是甩一份长文档让用户看:

1. **先自己摸**:读码、查现状、搜 memory 和仓库规范,把能自己回答的问题全部自己回答——**能查到的不许问用户**。
2. **剩下的关键决策点,一次问一个**:每个问题带自己的推荐答案和理由,让用户能用一个"嗯"确认或一句话纠正;问题总数 3 个上下,问不到点上不如不问。禁止开场甩完整方案或长清单等用户批阅。
3. 讨论收敛后,把结论压成 ≤5 行**意图契约**,原样进 PR 描述——契约是讨论的产物,不是让用户填的表:
   - **目标**(一句话)与**非目标**;
   - **行为契约**:对用户可见的行为承诺;
   - **失效契约**(涉及会话/账号/tab/端切换必写):切换时哪些状态/缓存/intent 必须失效重置——2026-07 实测:返工最重的 3 个 PR,bot threads 约一半在追"切换后旧状态残留";
   - **验收清单**:怎么算完成、怎么验证;**无法真实验证的面明确列出**"未验证 + 用户可执行的验证步骤",不默默交付。
4. **意图契约必须落盘（强制，不再限于长任务）**:`git-start.sh` 建 worktree 时已生成模板到 `$(git rev-parse --absolute-git-dir)/cindy-intent.md`（不进仓库、不污染 diff）。**动手前填完三段**——目标（一句话）、**非目标**、验收清单；`pr-size-gate.mjs` 会检查，未填不许开 ready PR。已有 worktree 没有这个文件的，自己照模板补一份。
   **「非目标」那段是这套机制的核心,不是凑数的。** 把容易被顺手带进来的邻域预先写死在那里（"不重构 X"、"不处理 Y 的历史遗留"、"不补 Z 的其它入口"）。后面 bot 提到这些时，你有一句可引用的书面依据去回复 + resolve，而不是每次临场判断"这算不算本 PR 的事"——**临场判断必输**，因为每条意见单看都合理。
   每轮 review 动手前和 push 前重读它，与 PR 描述、最早用户目标核对；产品目标变化先问用户，不让 bug 修复悄悄改写目标。
5. 用户提出"一次做到极致/别再返工"类要求时,契约必须让用户过目确认；单文件、无状态的小改动免讨论,直接记录目标与验收即可。

**PR 粒度按产品完整性决定:**

- 一个 PR = 一个连贯、可验收的产品目标，不等于一个技术层或 400 行代码。协议、服务、界面等拆开后任一阶段不可用，或会长期干扰正式功能时，保留为一个完整 PR。
- 只有各部分能独立使用、独立验证、独立合并且不会制造长期依赖时才拆；不要为了行数、review 方便或“地基先行”制造一串半成品 PR。
- 400 行只作为“需要更清晰说明与审查”的风险信号，不是强制切分线。大型但完整的功能用清晰意图契约、逻辑 commit、分区说明和完整检查补偿。
- **但"它是一个完整目标"这个豁免不能自评通过,必须过下面的客观检验**。2026-08-02 #1386 实踩:需求是"设置页三个入口收敛成一个 AI 引导按钮",交付出来是 +3604 / 49 文件——真正对应需求的只有 73 行按钮 + 119 行测试,其余是顺手做掉的 macOS 系统分组回写、device-link 同步线路、Apple 锚点设备边界隔离。它的 PR 描述写得极其详尽、每一块都有理由,**而详尽的描述恰恰是"我觉得它完整"的自我说服过程,不是完整性的证据**。三问,任一答不出就是多目标捆绑、该拆:
  1. **目标能不能一句话说完**,中间不用"同时/并/另外/顺便"来连接?
  2. 用户拿到这个 PR,**少了其中任一部分是否就不可用**?能单独用的部分就能单独发。
  3. 描述里的"本 PR 包含"是不是一个**列表**?列表长度 > 2 基本等于目标数 > 1。
- 开 ready PR 前跑 `node ~/.agents/skills/git-workflow/scripts/pr-size-gate.mjs`（见 Publish 步骤 1.5）——开局就贪大的 PR 没有漂移可测,只有入口规模能兜住,而且它不需要 PR 号,是唯一能在"还来得及拆"的时刻生效的闸门。
- 无关重构、纯格式化、依赖升级仍应剥离；是否拆多 PR 属产品交付决定，不能由 agent 自行扩大，拿不准先给用户一句话建议。

## PR 工作单元与生命周期（单件流，2026-08-05 定稿）

**不变量:1 会话 = 1 PR = 1 worktree = 1 份意图契约。**一个 session 同一时间只 own 一个 open PR;收口(合并/关闭)后才接下一个,或直接开新 session。**唯一例外**:堆叠链(PR 间有依赖、共享同一目标)算一个交付单元,可同 session。标题的多段格式(`#A | #B`)只服务堆叠链与历史会话,新活默认单段。

为什么(2026-08-04 实证):一个同时挂四个 PR 的会话接了不属于自己的转交、往别人分支推了 3 个反向 commit,衍生 PR 全废。结构原因:① owner 忙碌信号是**会话级**的——一个会话修 A 的 review 时,B/C 的转交全部排队,"多 PR 的队列问题"正是单会话多 PR 制造的,拆开后各 session 空闲等自己的活,天然并行;② 意图契约、冻结(--pause)、身份校验全是 **per-PR/per-worktree** 粒度,多 PR 会话让每道闸都变糊;③ 爆炸半径:一个会话犯糊涂毁掉名下全部 PR。

**生命周期四节点(每节点用既有工具,节律固定):**
1. **出生**:`git-start.sh`(fetch 真上游 → 从上游默认分支建 worktree → 契约模板)。禁止从本地旧 main / 当前 HEAD 起分支。宿主建的 worktree 由 `pr-size-gate` 补契约,依赖按 projects/<repo>.md 自装。
2. **每轮 review 修复动手前**:`align-branch.sh`。BEHIND 且(落后 >200 或 diff 与上游新合并改动撞文件)→ 先 merge 最新基线再修(merge 不 rebase,squash 合并时自然抹平);DIVERGED → 停手,按「并行会话礼让与接管」查谁动了分支。
3. **ready 前**:强制 merge 最新上游 + 统一验证(见 Publish 步骤 2)。
4. **死亡**:收口三件套 → worktree 保留 ≥72h → 清理前查 Cindy DB 无 active session 绑定 → 含 submodule 用 trash(见「收口」)。

基线新鲜度由「本地基底保活」schedule 每 2h 维护,preflight 检查4 兜底——agent 不需要自己记"该 fetch 了",节点 2/3 会强制对齐。

## 决策考古（条件门禁）

## 范围纪律（上游 PR）

- **个人工作流/环境适配类需求不进上游 PR**——一律先找仓库**既有**的配置/env 覆盖机制解决（通常零代码即可）;拿不准是"通用修复"还是"个性化需求"就先问用户。
- 已混进去的：撤回对应 PR（close + 留说明），从整条分支链 revert 剥离，更新所有相关 PR 的描述与互链编号。
- 用户没要的功能不顺手加。已加又被判定超范围的：**行为整体剥离**,纯数据字段（additive、无行为）可保留作将来地基,但要注明理由并向用户确认。
- reviewer/bot 建议若与用户或产品负责人**已定的范围决策**冲突（如已剥离的功能被建议加回）,不照单全收——用决策依据回复并 resolve;拿不准先问用户。
- **范围升级熔断**:会话中途把小修需求升级为多阶段/多 PR 架构重写（无论源头是用户一句话还是 agent 提议）,动手前必须把**执行粒度**拿给用户确认:预计拆几个 PR、每期多大、后一期依赖前一期是否已验证——只确认方向不算确认。**这条确认必须走飞书**(见「驱动分界线」的「怎么问」);**为收敛 review 而新开一个 PR 是本条的典型命中**,不是技术细节,不许自行决定。**验证顺序倒置为先**:先用最小原型/直连实现验证目标效果,再决定要不要建抽象层;禁止"先合并地基抽象、后做验证性接线"（2026-07-25 实踩:#403 一个换选择器的小需求升级成 5 期重写,~70% 花费($366)落在无消费者的抽象层与被叫停删除的分支上;用户诉求最终由一个基于干净 main 的小 PR 解决）。
- **跟进/查询类请求默认只读**:"帮我看看 PR 进度/需要做什么"边界 = 只读查询 + 行动建议清单,不含开新分支、写代码、开新 PR、跑多轮自审。用户给出开放式授权（"按这个标准推进"）时,先把授权转成逐项清单（标明查询类/开发类）,开发类另起会话或至少给出明确交付点再动手（2026-07-26 实踩:一个"跟进进度"会话自行关 1 个 PR、新开 2 个 PR、跑 7 轮自审,$108）。

## 驱动分界线（自己推 / 问用户 / Slack 找人）

自动化必须带判断,每个待办先归类再动手,不归类不动:

**自己硬推(不问):**
- 可验证的技术修复:测试/类型/lint/CI/构建、可复现的 bug、安全问题、性能退化。
- bot 意见中可定位可验证的真问题;误读/过时意见用证据回复 + resolve。
- 文档、注释、格式、i18n 对齐等无行为影响的整理。

## Code Review 质量标准

ready PR 前必须先按意图契约走一遍真实用户路径，再按以下六维度 self-review；代码看起来正确但核心功能不可用，不能交付。draft 只检查无敏感信息、基本可读、不会误合并，并明确未完成项，不要求完整六维自查。

**对抗式预审（按风险触发）**:跨模块/跨端、大型功能、安全/权限/数据迁移、并发状态、支付或正式发布前，六维自查后用 1 个独立 reviewer 对完整 diff 做一次对抗式 review；小型、局部、低风险改动由主 session 自审即可。review 修复阶段先收齐一整批意见、全部改完，再统一自审；不在每个小修或每次 push 前机械重复独立审查。重点按「bot 高频主题」扫:
- **切换/dispose/登出后的旧状态残留**:账号/工作区/会话切换时 intent、cache、frame、游标是否失效重置;迟到回调是否用当前 state 而非闭包快照
- **异步窗口并发**:回调/请求 in-flight 期间穷举用户可能动作(增删、切换、重复点击、关闭)
- **失败路径顺序**:先推进游标/时间戳/标记、后执行删除/写入类副作用 = 失败即永久跳过(实挖:sweepExpiredRows 在 DB delete 前就前移 lastGlobalSweepAt)
- **重复事件幂等**:isFinal/重试/回调重入是否去重(实挖:isFinal 重复事件拼出重复终答)
- **清扫/TTL/兜底路径的入口覆盖**:清理逻辑只挂在其中一条流量路径 = 其它入口永不清理(实挖:TTL 清扫只挂 hook 流量路径)
- **容器语义**:淘汰策略插入序 ≠ LRU;缓存/落盘数据语义变更必须升版本作废旧数据
- **fire-and-forget 的挂靠**:异步写入是否纳入 pending 操作集,切换/退出时会不会漏
预审发现的有效问题在同一批修完；误报、过时意见或要求改变产品目标的建议用证据处理，不为留痕制造额外流程。

### 1. 安全性（零容忍）

- 无硬编码 secret / API key / token / 密码 / private key
- 无 SQL injection / XSS / command injection 风险
- 敏感文件不入库（.env、credentials、*.pem、*.p12）
- 权限边界正确（不越权调用、不暴露内部接口）;**给自动化会话/子进程的权限模式按最小必要给**,能 acceptEdits/沙盒就不给全放行
- 用户输入经过验证和转义后才参与逻辑;IPC/API 边界对枚举参数做运行时校验

### 2. 架构与可维护性

- 单文件不超过 500 行（有充分理由时标注原因）
- 函数/方法不超过 80 行（复杂流程拆子函数）
- 无重复代码块（3 处以上相似逻辑必须抽象）
- 依赖方向清晰（无循环依赖、不跨层直调底层实现）
- 新增模块有清晰的职责边界和命名
- 不引入不必要的新依赖（能用现有工具/标准库解决的不加包）

### 3. PR 完整性与可审查性

- **自查用命令,不用感觉**:`git diff origin/<default>...HEAD --stat` 看总量与逐文件规模;单文件/函数超标（500/80 行）同样以此核对,不凭印象放行
- 一个 PR 对应一个完整用户结果；体量大时用分区描述和逻辑 commit 降低审查难度，不按技术层强拆半成品
- 超过约 400 行时检查是否夹带无关工作、是否仍能清楚解释和验证；完整功能可保留，无关重构/格式化/依赖升级必须剥离
- 拆分必须保证每个 PR 独立可用且不会因合并时差长期冲突；否则宁可一个较大的完整 PR

### 4. 正确性与健壮性

- 对称改动（改了写查读、改了序列化查反序列化、改了 API 查调用方）
- 边界条件（空值、零值、极大值、空数组、并发竞争）
- **竞态高发区专查**：异步加载完成前的写入、内存态修复是否会被落库/持久层打穿、TOCTOU（检查与使用之间的窗口）、dispose/登出后的迟到回调
- 错误路径有合理处理（不吞异常、不返回 undefined 当成功）;安全拦截类逻辑 **fail-closed**（读取失败=拒绝,不放行）
- **异步窗口穷举**:回调/请求 in-flight 期间,穷举用户全部可能动作（增删、切 tab、切账号、重复点击、关闭）——回调用当前 state 不用闭包快照;同一异步窗口的坑**一次修完**,不逐个补（2026-07 实踩:同类并发坑连踩 3 轮,每轮修复又引入新 P1）
- **删兜底先补护栏**:移除任何静态 fallback/默认值前,先写"上游成功但结果退化"的确定性护栏（数量下限/保留上次快照）;没有护栏不许删（2026-07 实踩:删静态清单后上游返回单条,全量模型塌缩）
- **兜底枚举按运行时取**:禁止把单一 agent/平台专属枚举值当跨平台 fallback
- **写路径对称**:状态落库时核对内存缓存、广播事件、runtime 推送是否同步更新
- 新功能有测试覆盖（至少 happy path + 主要错误路径）;修 bug 必须带回归测试
- 数据库/持久化变更有迁移方案

### 5. 代码卫生

- 无遗留 TODO/FIXME（要么解决,要么开 issue 追踪）
- 无 console.log / print / debugger 调试残留
- 无注释掉的代码块（删掉,git 有历史）
- 无混入的无关空行/格式 diff
- 命名自解释,注释只解释 why
- import 整洁（无未使用引入）;i18n key 各语言对齐、无孤儿 key

### 6. UI 视觉自查（改到用户可见界面时强制）

- 开 PR 前**必须亲眼看过改动效果**,至少一种方式:起 dev 实例/预览页真实操作一遍;或写个静态 harness 页面渲染改动组件。类型/测试绿 ≠ UI 对。
- 至少覆盖:默认态 + 空态/加载态 + 深色模式（项目支持的话）;有交互的过一遍交互。
- 验证结果写进 PR 自测确认(截图或"已在 dev 实例过目 + 覆盖了哪些态");没看过就如实写没看过,不糊弄。
- 纯逻辑/后端 PR 免此项。

## 安全门禁（commit 前）

`git add` 之后、`git commit` 之前:

1. **敏感字符串扫描**:
   ```bash
   git diff --cached --name-only | xargs grep -lnE \
     "(API_KEY|SECRET|PASSWORD|PRIVATE_KEY|ACCESS_TOKEN|aws_secret|client_secret)\s*[=:]\s*['\"][^'\"]{8,}" 2>/dev/null
   ```
   命中则确认是否 placeholder/example;否则移除后再 commit。

2. **敏感文件检查**:staged 中不应有 `.env`、`*.pem`、`*.p12`、`credentials*`、`*secret*`。

3. **大文件警告**:新增单文件 >1000 行,确认是否应拆分或是否生成物。

4. **gitignore 覆盖**:项目 `.gitignore` 应包含 `.env*`、`*.pem`、`node_modules/`、`dist/`（按语言适配）。

发现违规 → **停止提交**,修复后重新 stage。

## Review Follow-Up

**触发方式（2026-08-01 批次握手）**:发完 ready PR **不守等** bot 首批意见。总管严格按 head 一次性交付:`owner 批量 push 新 head → checks 全终态 + 仓配置声明的 review bot 全部完成该 head → 总管只投递一份全量 handoff → 同一 head 静默到 owner 下次 push`。owner 的 follow-up 从收到总管 handoff（或用户点名）开始；禁止逐 bot、逐 thread、逐 check 轮询。

**收到 HANDOFF 先验身份（强制,第一动作）**:处理任何转交前,先用宿主 `get_current_session_id` 取本会话 id,与 `sweeps/<owner>_<repo>.json` 里该 PR tracked 条目的 owner 比对。**不一致 → 拒收**:回一句「本会话非 #<N> 的 owner(登记 owner 是 <前8位>…),不执行」,然后不改码、不回 thread、不 resolve、不碰 PR 状态。写侧的 preflight 检查5 只是第二道锁——等它拦截时,GitHub 侧的操作(resolve 线程 / 转 draft / 评论)早已做完,它一个都拦不住(2026-08-04 #1581 实踩:非 owner 会话接了转交,resolve 了 5 条线程、把 PR 转成 draft、往分支 push 了 3 个与 owner 方向相反的 commit)。确要转移 owner:先 Chris 确认,再 `hb-register.mjs` 重新登记覆盖,才算换手。

**follow-up 被打断必须接续（强制）**：follow-up 轮次因用户插话 / 工具被拒 / 会话切换而中断的,是"暂停"不是"取消"——处理完插入话题后**第一动作**回到中断点把整轮跑完（拉 threads → 修 → push → 回复+resolve → 验证归零）。中断点若是"等 bot 出意见",接续动作 = 确认心跳已登记该 PR,然后结束回合交给 settle 转交,不留悬空等待（2026-07-09 实踩:首轮等待被打断后未接续,Codex P2 挂了一整天直到心跳催）。

1. **分层查看,不混层级**:checksSummary / reviewDecision / latestReviews / GraphQL `reviewThreads`（`isResolved` / `isOutdated`）。**不把单个 check pass 说成 PR 通过**;不能只看 flat comments——顶层 bot summary 要单独读,它可能含 diff 外的意见。
2. 分类处理，**完整 review wave 没收齐前不开始逐条改**:
   - **第 0 步:回读意图契约,逐条做相关性判定（在任何归类和动手之前）**。打开 `$(git rev-parse --absolute-git-dir)/cindy-intent.md`,把「目标」和「非目标」两段读一遍,然后对**每一条** review 意见回答一个问题:
     > **这条意见解决的,是不是「目标」那一句话里写的那个问题?**
     
     答案不是"是" → 直接归**推**(外推 issue 或不处理),不进本轮修复清单,不管它多有道理、修起来多快。命中「非目标」段的,引用那一行回复 + resolve。
     
     **这一步为什么必须机械执行**:review 意见的说服力和它是否属于本 PR 无关。2026-08-04 #1636 的四轮意见——edit 要核验身份、deleteMessage 也要、uploadImages 跨 await 每次都要、多组上传中途换 owner 也要——**每一条都是真问题,每一条都能写出复现路径**,合起来把一个"终稿消息丢失"的 bug 修成了 +1071 行的身份核验体系。当时没有任何一步要求回答"这是不是我要解决的那个问题",于是每一轮都顺理成章。有了这一步,第二条就该被判"推"。
     
     判定结果**写进本轮的修复记录**(一行一条:意见 → 修/答/推 → 依据),不要只在脑子里过。写下来才能在第三轮时看出"我已经连续三轮在修同一族的东西了"。
   - **设计意图优先于 review 意见**:bot/reviewer 建议若要求改变原方案、行为契约或加没要的东西 → **不改码**,用设计依据回复 + resolve,或按「驱动分界线」问用户。实现方式可以按意见改,意图不能被 review 冲掉;每轮修完自查:改动后行为仍符合 PR 描述的目标吗。
   - **技术问题 AI 自主处理**:正确性、可靠性、测试、CI、性能、安全、架构及可验证的小问题，只要意见有效且不改变产品目标，本轮全部处理；按根因覆盖所有受影响位置，不按 reviewer 或文件拆成多轮。
   - **AI review 是一等输入**:Codex/Greptile/Copilot/bot 的建议可定位可验证就当正式 review。bot 拿"fresh evidence"追问上一轮修复时优先核实——常见真问题是内存态修复被落库/持久层打穿。
   - **范围核对**:意见与已定范围决策冲突时按「范围纪律」处理,不照单全收。
   - **不偷懒切 scope**:本 PR 引入的债在本 PR 内闭环,除非远超范围。
   - **只把产品决策交给用户**:方向、UX、优先级、敏感/权限、公开承诺。
3. **push 前先本地 self-review**:review 修复不是免检的。用本地 review 工具或对抗式 review agent 以 bot 同视角扫增量（大改动扫全量 diff）,把能发现的一次修完,每分支**合批成一次 push**——不要修一条推一次。

   **push 前漂移门禁（强制,不是建议）**——第二轮及以后的 review 修复,push 前必须跑:
   ```bash
   node ~/.agents/skills/git-workflow/scripts/pr-drift-check.mjs <PR号>
   ```
   - `PASS` → 继续 push
   - `WARN` → 读完 ACTION,确认不是在往漂移方向走再 push
   - `STOP` → **停止,不许接着修下一条意见然后 push**。除下面的收尾豁免外,STOP 的默认动作是**冻结,不是继续想办法**:执行 `hb-register.mjs <owner/repo> <PR号> --pause "drift STOP"`,然后按「怎么问」飞书报 Chris(现状数字压到三行 + 三选一:继续修 / 缩回正题重发 / 关闭),他裁决前不再 push。"必须拆"或"要改产品目标"是产品决策,不自行执行。(2026-08-04 教训:STOP 后走"摆选项菜单让 Chris 选"的软处理,选出来的 #1612 底座 PR 本身就是被 review 带偏的产物,最终作废——STOP 时唯一可靠的默认是冻结。)

   **收尾豁免（重要,否则门禁会在每个 PR 的最后一轮制造假警报）**:PR 已进入收尾——本轮意见修完后 unresolved 归零、不再新增功能面、只等 CI 与 approve——此时 `STOP` **不适用**,正确动作是推完收口。走到这一步再回头拆分,是把已经付出的十几轮 review 成本二次浪费掉。用豁免时在汇报里写一句"已收尾,drift STOP 不适用"。**豁免不能当常规绕过理由**:只要本轮还在往 PR 里加新的代码面,豁免立即失效（2026-08-03 判例:#1376 十六轮、#1405 九轮均判豁免直接收口;同批的 #1386 判必须拆——区别是 #1386 属**目标错配**,用户要一个按钮却交付 49 文件的附加功能,而前两者的增量都在原目标内,只是量大）。

   **STOP 之后,真问题去哪了**:冻结不是"放着 bug 不管",是把处置权交还 Chris。他裁决「继续修」→ 命中「必须留在本 PR」四条的照修(见「Bot 复审循环收敛」的三分法);裁决「缩回正题重发」→ 这些问题跟着正题进新 PR;其余归「推」外推 issue。若你诊断出"同一根因被反复触碰、需要重构或拆出独立设计",那个诊断本身就是报给他的选项之一,**不是自行开工的授权**。(本段 2026-08-04 改写:旧版允许 STOP 后继续"重构一批推",正是 #1581 越修越大的通道。)

   脚本查五项:review 循环强度（address-review commit 累计数）、review 阶段规模漂移（相对进 review 前的净增长）、**已回应但未 resolve 的线程**、绝对规模、工具链容量信号。阈值 2026-08-02 按 10 个 PR 首次校准(合并的 6 个全 PASS,卡死的 4 个全 STOP);2026-08-04 收紧:循环强度改为 WARN≥3 / STOP≥4(对齐 3 轮硬上限),绝对规模改按**非测试代码**口径(WARN 400 / STOP 800,与入口闸 pr-size-gate 的 150/300 衔接)。

   **旧判据为什么失效（重要,别再用它自查）**:原本写的是"同一分支一小时内 ≥3 次 push"。2026-08-02 实测 commit 间隔稳定在 **28±5 分钟**——正好是 CI 一轮 + bot review 一轮的时间,一小时只有 2 次,**永远卡在阈值之下不触发**,于是 #1371 振荡了 19 轮 / #1376 19 轮 / #1405 14 轮全程无警报。真正有判别力的指标是**累计** address-review commit 数（健康 PR 昨晚最多 1 个,卡死的 9/16/18 个）,不是单位时间频率。感觉不到自己在振荡是正常的——每一轮单看都很合理,所以必须靠脚本量。
   处理 review threads 同理**批量化**:一次性拉全量 unresolved 列表→按文件/严重度分组→批量修完→一次性回复+resolve,不做"查一条→改一条→回一条"的单条循环。
4. 修复后跑验证（含新增回归测试）,commit/push,只 stage 相关文件。
5. **resolve 前在 thread 留可见回复**;bot 在 push 后自动 resolve 的 thread 也补一条可见回复留痕。误读/过时的意见用证据回复后 resolve。

   **回应即 resolve,不留"已回应未 resolve"的悬空线程（2026-08-02 实踩,当晚 4 个在飞的 PR 全部踩中同一个坑）**:只要还剩一条 unresolved,auto-review 就跳过**整个 PR**——不审查、不合并,而且除了 gate bot 每晚一条提醒之外没有人会告诉你。#1371 在 19:42 就完整回应了那条意见并给足了三条硬约束依据,只是忘记点 Resolve conversation,白卡 5 个多小时,CI 全绿也没用。**回复完当场 resolve**;刻意留给放行人裁决的线程,在 **PR 描述里显式写明"哪条线程等谁裁决"**,别让它静静堵着整个 PR。`pr-drift-check.mjs` 第 [3] 项专门查这个,它把"等我回应"和"我已回应但没 resolve"分开算——后者是纯流程失误,零成本可修。
6. 重查所有维度确认闭环:unresolved=0、checks、reviewDecision、pending review 清零。**闭环后更新会话标题状态段**(`修review`→`待bot`,或 approve+绿→`待合并`;格式见「收口」节)。

### Bot 复审循环收敛

bot 每次 push 都会全量复审,永远可能再挖出新东西——不设收敛机制就是无限烧 token 的循环:

- **一轮一个闭环**:等仓库声明的所有 review board 与 checks 收齐 → 主 session 读完全部有效问题 → 按根因一次性修改所有受影响位置 → 统一 self-review → 按影响范围统一测试 → 一个修复 commit、一次 push。禁止边改边测、修一条推一条或每个 reviewer 单开一轮。
- **意见三分法(每条意见先归类再动手,不归类不修;归类之前先过 Review Follow-Up 第 0 步的相关性判定)**:
  - **修**:两个条件**同时**满足才算——① 通过相关性判定(它解决的确实是意图契约「目标」那一句里的问题);② 命中「必须留在本 PR」四条(regression / 本 PR 使其可达 / 交付体验依赖它 / 正确性·安全类且本 PR 代码路径走到)。只满足 ② 而与本 PR 目标无关的,仍归「推」——**"它是个真问题"从来不是把它放进这个 PR 的理由**。
  - **答**:误读、过时、纯偏好、与既定范围决策冲突的——证据回复 + resolve,不改码。
  - **推**:加固、邻域边界补全、通用能力、"顺手补完整"类——**即使是真问题,默认外推 issue**(按「外推 issue 的边界」),不在本 PR 修。bot 在你改动邻域挖出的东西不天然属于本 PR。2026-08-04 实踩:#1636 一个"终稿撞编辑 flood 丢消息"的 bug,被逐轮扩成"全部出站入口的回合身份核验",+1071 行、review 阶段漂移 +182%——每一轮单看都合理,合起来主体已不是原 bug。
- **轮数硬上限:一个 PR ready 后最多 3 轮 address-review 修复**(一轮 = 收齐完整 wave → 合批修 → 一次 push)。第 3 轮 push 后又来新 wave → **不再修**:执行 `hb-register.mjs <owner/repo> <PR号> --pause "review 超轮数"` 冻结跟进,按「怎么问」飞书报 Chris 三选一(继续修 / 缩回正题重发 / 关闭),他裁决前一行码不改。他说继续修才恢复登记,恢复后每再 +2 轮重新触发本条。**本条取代旧的「能修则全修,不设轮数停修」**——那条教义是 2026-08-04 三个 PR(+2504 行)全废的直接原因:#1581 的 415 行正题被 8 轮 review 泵成 1097 行后关闭重做。上限不是"放着 bug 不修",是把"还值不值得在这个 PR 里继续修"升格为产品决策。
- **重复出现就升级根因处理**:同一底层逻辑连续多轮被不同 finding 触碰,暂停局部补丁,重新梳理完整状态/数据流,一次覆盖全部入口——但这仍算一轮,不豁免轮数上限;梳理结论是"要重构/要拆出去"时,按 --pause + 问 Chris 走,不自行开工。

### 范围漂移与问题替换

review 循环不只是烧 token,它会**悄悄改掉这个 PR 是什么**。规模能量,主体漂移不能量——必须主动核对。

- **判据**（`pr-drift-check.mjs` 第 [2] 项自动算）:以"进 review 循环前的最后一个 commit"为基线比当前净增长,超 +50% 要能解释,超 +150% 停下重估。算法上**每个 commit 都对它自己的 merge-base 算 diff**,否则 merge 上游带进来的代码会把统计打成噪音（用固定 base 会看到 244 → 16640 这种假暴涨,判据就废了）。
- **2026-08-02 #1376 实测**:初始 244 插入 / 8 文件的「自动 worktree 改用远端默认分支为基底」,19 轮 review 后成了 1759 插入 / 16 文件（**7.2 倍**）,而增量的大半在做一件与标题无关的事——手写跨平台进程树终止（POSIX 进程组回收、Windows `taskkill /T /F`、进程表快照、血缘闭包追踪、收尾看门狗）。PR 的主体已经不是它声称的东西,全程没有任何机制喊停。
- **处理顺序**:① `git diff <mergeBase>...HEAD --stat` 看改动最多的文件,对着 PR 标题与意图契约逐个回答"这属于原目标吗";② 不属于的**整块剥离**另开 PR;③ 属于原目标但本质是通用能力的（进程管理、重试、并发原语、跨平台兼容）,先找成熟方案,**不在业务 PR 里手写试错**——bot 能就同一个状态机连撬十几轮,恰恰说明这块不该在这里现写。
- **工具链撑爆是"该拆了"的信号,不是"该加内存了"的信号**:PR 大到 typecheck OOM / CI heap 不够时,加容量可以做,但同一回合必须回答规模问题（#1371 两个 commit 分别降推断开销、抬 desktop heap 上限,同晚还催生了把仓库级 CI heap 提到 8GB 的 #1403）。
- 反过来,**开局就贪大的 PR 没有漂移可测,只能靠绝对规模闸门**（第 [4] 项兜底）。「全面改版」这类标题本身就是范围声明,等于放弃增量交付——写下这四个字之前先问用户要不要分期。

### 不属于本 PR 的问题:外推 issue 的边界

这是收敛 review 无限扩展的**第二个工具**（第一个是上面的根因升级）。bot 会在你改动的邻域挖出一切能挖的东西,全部就地修 = PR 无限膨胀;全部推走 = 已知缺陷进 main。分界靠下面的规则,不靠感觉。

**第一步永远是切层,不是判"推不推"。** 别问"这个问题要不要推出去",先问"这个问题分几层,本 PR 的改动落在哪一层"。2026-08-02 #1371 的标准姿势:bot 报「插件 webview 跨账号共用存储分区」,它切成两层——**面板宿主不随 owner 重挂载**那层属于本 PR 的改动面,当场修（`3270cf8e`:owner 键清空 `openPanelId` + 宿主 key 纳入 owner 代际 + 判据抽纯函数加单测）;**分区即存储层**那层外推 issue #1411。resolve 回复里显式写明两层分界,防止后来人以为整个问题都没修。切层做对了,边界基本就对了。

**必须留在本 PR（任一命中就不许外推）:**
1. 本 PR 引入的（regression）——你带进来的债你还。
2. 本 PR 让它**变得可达或更易触发**的:问题原先存在但入口没打开,你的改动打开了 → 等同于你引入的。
3. **本 PR 声称交付的体验依赖它**:那就不是"另一个问题",是本 PR 的功能不完整。要么修,要么把依赖它的那部分功能一起撤下不发——不许发一半体验然后把缺口挂在 issue 上。
4. 正确性 / 数据安全 / 权限 / 凭证类,且本 PR 的代码路径会走到它。即使是存量问题也要修,或至少改成 fail-closed 并说明。

**动手之前的第一个问题是"这会把本 PR 的评审面扩大多少",不是"怎么修"。** 一旦开始盘算实现方案（阈值调 85 还是换假时钟）,你已经默认了这笔账只有实现成本——而实现成本恰恰是这笔账里最小的一项。

**正当的外推理由（必须具体、可引用到规则或门,不能只说"超出范围"）:**
0. **跨边界的流程成本远大于实现成本**——最常被"顺手"违反的一条,单独列在最前。**改别人的代码本身不是禁忌**,判据不是所有权、不是礼貌、也不是行数,而是成本核算,且必须算两笔:
   - **实现成本**:改这个东西本身要多久。agent 默认只算这一笔,于是"修法很轻""两行就好"永远成立。
   - **流程成本**:并进本 PR 会触发什么——多一个 reviewer、多一道评审门、bot 对新 head 全量重审、CI 全量重跑、排队等人 approve。这笔是**小时级且不可控**（取决于别人何时看、bot 何时出意见、队列多长）,而实现成本是分钟级。差几十倍。
   还要说清**它想省掉的是什么**:如果省掉的是"重跑 9 分钟"这类**可控、确定、有界**的成本,那么用几小时不可控成本去换,是明显负收益。**agent 对超出边界的工作必须用更高的成本预算门槛**——不是"这活小所以顺手做",而是"这活会把我的 PR 拖进多长的不可控队列"。推论:**改动大小不是判据,是否扩大评审面才是**;同样两行改动,落在本 PR 范围内只增加 diff,跨出边界就增加评审面。
   2026-08-03 实踩:#1371 收尾时发现 `packages/maker-core` 的 app-server 超时用例在 Windows CI 上因墙钟阈值（70ms）过紧而间歇性假失败,**已两次把本 PR 卡红、每次重跑 9 分钟**,agent 据此提出顺手修（放宽到 85 或改用假时钟）,并把它描述成"修法很轻,两条路选一"。用户拦下:「改别人的没问题,但是这会无限扩展,改一个 PR 就会遇到无数的审核和排队,这又会是几小时,成本远大于 9 分钟,那个不可控」→ 开 issue #1416 收口,一字节不碰。**被拒绝的理由很有诱惑力——"它正在伤害我的 PR"是真的**,但那 9 分钟是可控的,并进来引发的审核与排队是不可控的几小时。
1. **修它会让本 PR 落进另一道评审门**——#1371:partition 属沙箱面,并进来就要走插件基座白名单确认门,而这是个 UI 改版 PR。
2. **修它需要存量数据迁移,本身就是独立设计**。#1371:分区名纳入 owner 会让已装插件的 localStorage / IndexedDB / Cookie 落到新空分区,等于强迫用户重新配置,必须配一套迁移。
3. 修它需要**产品决策**（行为契约 / UX 取舍),不是技术问题。
4. **存量问题,本 PR 只是路过**:bot 因为你改了邻近代码才发现的老问题。

**防滥用的硬约束（用户 2026-08-03 明确要求"控制好边界,不然任何问题都提出去"）:**
- **外推 = 开一个真 issue**,不是在 thread 里说"后续再看"。issue 必须含:复现或**代码位置（文件:行）**、为什么不在本 PR 修（引用具体规则/门）、影响面、验收标准。#1411 是合格样例:五个消费点全部带文件行号,验收标准里写明"升级无感:老用户不需要重新登录/重新配置"。
- **每个 PR 外推上限 2 条**。超过就是信号——要么这个 PR 建在一片沼泽上,要么你在系统性逃避,停下问用户。#1371 二十条线程只外推 1 条,其余全部真修。
- **在 PR 描述里显式列出外推清单 + issue 链接**,不许只埋在 thread 里。放行人认的是**透明**,不是理由本身;埋起来的外推等于让放行人替你背没看见的风险。
- **功能 bug 外推必须在 issue 里写明"修好之前用户会遇到什么"**,并在 PR 描述的外推清单里标出来。已知功能缺陷进 main 是有真实用户代价的决定,要让人看得见才能反对。
- resolve 回复里做**边界澄清**:本 PR 修了哪层、issue 是哪层。少这一句,记录会被读成"这个问题被无视了"。
- **被拒绝的是"并进本 PR",不是"改"**。既然成本出在评审面扩大,那么**另开一个独立小 PR 去改就是合法出口**——它的评审面只有自己,不污染当前 PR。所以跨边界的东西有三个出口,按当前 PR 的紧迫程度选:① 开 issue 交给归属人（不紧急,或改法涉及别人的设计意图而你没把握）;② 自己另开独立 PR 改（确实在阻塞你,且改法有把握）;③ 先重跑绕过、issue 记账,等本 PR 收口后再处理。**唯一不许的是并进当前 PR。**
- **外推 ≠ 开完 issue 就不管**。像 CI flake 这种会反复卡红后续每个 PR 的,issue 正文要写明**已阻塞哪几个 PR、各卡红几次、每次重跑代价**——这些数字才是它的优先级信号,只写现象和修法等于一条技术备忘。然后按「主动 Slack 找负责人」推进,或回来问用户要不要走出口 ②。中间态明确:**重跑 + 记账 + 升级,不是沉默忍受**。
  - **归属人是外部 contributor 时 assign 这条路是堵的**:GitHub 不允许 assign 非 collaborator,`gh issue edit --add-assignee` 会报 `'<user>' not found`——那是权限问题不是 handle 拼错,先用 `gh api repos/<o>/<r>/collaborators/<user>` 区分（404 = 非 collaborator）。这类情况靠 issue 正文里的 `@mention` 送达（mention 对任何真实用户都生效),再不响应走 IM。开源仓大量模块由外部贡献者维护,别把 assign 失败误判成"人找错了"。

### 心跳转交的经济性（owner 端）

sweep 侦测端已是轻量,但转交进 owner 主会话后由主力模型处理——2026-07-26 实测:owner 对每条转交默认重走一遍 `gh pr view` + GraphQL threads 分页 + diff 复读,单会话中转交响应吃掉全部工具调用的 45%,而大量转交本身写明"无变化/无需处理"。

- **先读转交结论,再决定要不要动**:转交消息已含 sweep 查到的 state/checks/threads 快照——结论是"无变化/无需处理/已知基线问题"时直接确认收悉,不重新拉取。
- 需要处理时,**验证范围只到被点名的文件/thread**,不重跑全量状态查询,除非转交自身提示快照可能过期。
- 同一 PR 短时间内多条转交且无实质变化 → 合并处理一次。

### 等待与轮询纪律

- 预期等待 >60s 的操作（CI、autoreview/codex 子进程、bot 复审、人工 review）:用后台任务起掉或移交心跳,**禁止 `sleep N` 阻塞主会话轮询**（2026-07-26 实踩:单会话 9 条 sleep 合计 44 分钟纯等待,占会话时长 34%）。
- 等 bot 出意见期间主会话要么做别的事要么结束本轮;"挂着等"就是烧上下文。
- 外部 review 工具的环境依赖（可执行路径、扫描器）在**第一次调用前**核查好,不要靠失败重试探路（实踩:5 次失败尝试才跑通 autoreview）。

### 评论通道故障排查

- inline reply 全部返回 422 → 大概率有**pending review 草稿**堵住该账号的评论通道（另一个 agent/会话留下的）。查出 pending review,把草稿以 COMMENT 事件提交发布后重试。
- `gh pr edit` 被 GraphQL 弃用错误（如 projectCards）阻断 → 改走 REST:`gh api -X PATCH repos/<owner>/<repo>/pulls/<n> -F body=@<file>`。

### 并行会话礼让与接管

心跳/跟进轮发现同一 worktree 或分支有**另一个 agent 会话正在工作**（几分钟内的新 commit、未提交的半成品）→ 本轮完全不碰:不提交它的半成品、不切分支、不代答 thread,直接 silence;下轮检查其是否收尾,悬置才接手。

接手时先全景盘点再动手:它的 commit 是否已推送、脏文件内容是什么、是否留有 pending review 草稿、分支拓扑是否被弄乱、有没有违反已定范围决策的改动（如把已剥离的功能加回来）。核实无内容丢失后:对的保留,错的撤,半成品评估后收尾或丢弃。

接手后**动手期间**同一 worktree 再次出现对方的新 commit(2026-07-18 实踩:盘点时看到的"未提交半成品"在我编辑期间被对方 commit+push)→ 立即停下重新 `git log` / `git status` 盘点,确认自己的编辑落在了谁的基础上、有没有互相覆盖,再决定继续;绝不在明知对方活跃时与其在同一 worktree 交叉编辑。最稳的顺序是接手前先等对方静默几分钟并 `git -C <worktree> log -1 --format=%ci` 确认最后 commit 已有一段时间。

## Merge Readiness

目标是把 PR 推到可合并:

- `isDraft`:实现+描述+自测+安全检查完成后才 ready。
- `checks failing`:查日志修到绿;基线问题给证据。
- `unresolvedCount>0`:逐条定位、修复或回复。
- AI reviewer actionable:按 Review Follow-Up 处理。
- `REVIEW_REQUIRED`:排除 AI 可行动项后汇报"等谁"。
- `BLOCKED`:查明原因;可控的修,权限问题交用户。
- **`BEHIND`(已 approve 但分支落后 base,仓库要求 up-to-date)**:`gh pr update-branch <N>` 或在 worktree merge 最新上游默认分支后 push(merge 不 rebase),checks 绿后**交仓库方合并,禁止自己合并**。这不是"干净无事"态——它既不产生 unresolved 线程也不是 conflict,却是唯一阻断(2026-08-05 实踩:#1685/#1700 双双 APPROVED+全绿+BEHIND,maintainer 催 3 小时无人响应;总管 v4.7 起由 behind 事件转交)。
- 全部满足:用户授权则合并;否则汇报 ready-to-merge。

## 排障与归因纪律

- **多机归属三查(Chris 多台电脑共用同一 GitHub 账号,这条在一切盘点/复查/接手判断之前)**:`gh pr list --author` 看到的是**所有机器、所有 session** 的产出;`origin/*` remote-tracking 引用一次 fetch 就全量同步——**这两样都不构成"本机做过"的证据**。2026-08-04 实踩:另一台机器的盘点会话从 GitHub 采集未合并 PR 状态,误当成本机最后做的调整,据此做出错误判断和决定。断言"本机/本会话做了 X"之前,按证据强度三查:
  1. **Cindy DB**——sessions / session_pr_refs 里有无绑定该 PR/分支的本机会话;
  2. **sweeps 登记**——tracked[] / ignore[] 里有无该 PR;
  3. **本地分支**——`git show-ref --heads` + `git worktree list`(必须是 refs/heads,**不是 origin/\***;且注意他机分支也可能被人为 fetch 到本地,如为参考代码专门拉取的场合)。
  三查全空 = 判「**他机或未知**」:只读、不推演、不处置——不计入本机工程状态、不据此评价本机会话的产出、不替它做修/关/转 draft/重做的决定,处置建议最多一句并注明「需在归属机器上执行」。盘点/复查类报告**必须分三栏:本机在做 / 他机或未知 / 已终态**。总管预检的「本机无分支→跳过(可能属其它机器)」是本纪律在自动化链路的既有实现,本条把它推广到一切人工触发的判断。
- **归因先查己**:断言"是别人/外部 pipeline 改的"之前,先 `git log` 相关文件的近期提交——**包括自己以往会话的产物**;本地落后 origin 时先 fetch 再下结论（2026-07 实踩:把自己参与的重构指控为"另一条 pipeline 覆盖",被用户反问才查历史更正）。
- 用户给的假设逐条验证,证伪要带证据;区分"根因"和"放大器",别把放大器当原因收案。
- **提"新增功能"方案前先盘点现状**:grep 现有实现,第一句先回答"现状已有什么"（2026-07 实踩:建议新增预设模板,UI 里已有模板功能）。
- 多个候选根因时按可能性排序,给出"先查这条",不把缩小范围整包交回用户。
- 设计/方案对齐仓内已有原则文档（配置分层、架构约定）,方案里显式写"与 X 文档核对过"。

## Commit 纪律

**PR 的 commit 历史是给 reviewer 和未来维护者看的叙事,不是开发过程的实时日志。**

### 实现阶段

- **一个逻辑单元一个 commit**:完成一个可独立理解的变更做一个 commit。
- commit message 用 conventional commits 格式（`type(scope): 简述`），说清这个 commit 为什么存在。
- 开发中的中间态用 `--fixup` 标记,开 PR 前统一整理。

### 开 PR 前（强制）

push 之前审视 commit 历史:
```bash
git log --oneline origin/<default-branch>..HEAD
```

- 先检查是否存在 fixup/WIP/含糊 message。需要 `git rebase -i` 做 squash/reword 时，**必须先取得用户对本次 rebase 的明确授权**；未授权则只报告历史问题，不改写提交。
- 已推送或属于堆叠 PR 的分支不得擅自 rebase；堆叠链继续按下文只用 merge。
- **目标**:每个 commit 可独立理解、message 有意义；该目标不凌驾于 rebase 授权门禁。
- 简单改动理想状态是 1 个 commit；若已经产生多个 commit，是否 squash 仍受上面的 rebase 授权门禁约束。
- 复合改动（如 refactor + feature + test）理想状态是按逻辑步骤保留 2-5 个 commit；未授权时不为追求数量改写历史。
- **最终合并由上游决定**:如果仓库配置了 squash merge,GitHub 会在合并时自动压成一个 commit——但这不是你在 PR 阶段放任脏历史的理由,reviewer 审的是你的 commit 列表。

### Review 修复阶段

- 一轮 review 的所有修复**合批成一个 commit 再 push**——不是修一条推一条。
- commit message: `fix: address review — <概括>`。
- 纯格式/nit 级有效意见也并入本轮修复，但不为它单独 push；误读用证据回复 resolve。
- **验证按批、按影响范围跑**:修改期间不在每个问题后插入全量测试；整批修完并 self-review 后统一验证。局部且边界清晰的改动跑定向检查即可；涉及共享接口、跨组件状态或并发时跑相关链路；Pi 这类大型功能、安全/数据迁移/发布前才跑完整检查。线上 CI/review 已覆盖的完整检查不在本地无变化重跑。同一验证只跑一次并保留完整结果。

### 堆叠 PR

- 底层未稳定前（还在被 review 修改）**不向上层频繁 merge**——等底层 review 通过、不再有改动后一次性合入上层。
- 堆叠链内**只用 merge,不用 rebase**（rebase 会重写已推送的 commit hash,在多分支共享 commit 时制造冲突地狱）。
- 底层合入 main 后,上层用 `git merge origin/main` 同步（不是 rebase）。

### 底线

- 不出现 `wip`、`tmp`、`fix fix`、`address comment`、`test` 这类无意义 message。
- 不为每次 bot 复审单独开一个 fix commit 然后立即 push（这是触发无限复审循环的元凶）。

## Publish

默认是实现、验证、按仓库既有方式同步。**只有用户明确要求 PR/MR/review，或仓库规则明确要求走 PR 时才创建 PR/MR**；“提交”“push”“发布”“同步到多台电脑”都不等于授权开 PR。

- Chris 的个人配置、skills、dotfiles、备份或多机同步仓默认在确认远端最新后直接 push 默认分支，不开 PR、不启用 review bot、不登记 PR 总管；只有 Chris 当次明确要求评审时例外。
- 其它允许直推的个人仓同样沿用现有直推方式；不要为了套流程自行制造 feature branch、PR 或 heartbeat。
- 确实需要 PR 时再按状态选择 ready/draft；**开 PR 不是本地改动或 push 的默认终点**。

- **ready PR**:实现完整、真实用户路径和相应层级检查通过、意图契约验收全绿，可以正式评审与合并。
- **主动 draft PR**:大型连贯功能需要尽早确认方向、工作会跨天/跨人、依赖尚未齐全，或继续写下去前早期 review 能显著减少返工时使用。描述明确已完成/未完成/不能合并的原因；只做最低安全与基本可读性检查，不跑完整发布门禁，不登记总管。
- review 后因产品/安全 gate 被转成 draft 是被动状态；解决 gate 后再 ready。实现已完成且无需早期协作价值时直接 ready，不为流程仪式先开 draft。
- **不开 PR**:探索/试验性改动,或用户没说要提交——保持 worktree,汇报结论即可。

1. 确认 diff 聚焦、无敏感文件、通过安全门禁、不含个人环境适配改动（见范围纪律）。
1.5. **入口规模闸门（强制，ready PR 前必跑，不是建议）**:
   ```bash
   node ~/.agents/skills/git-workflow/scripts/pr-size-gate.mjs
   ```
   - `PASS` → 继续
   - `WARN` → 确认没夹带无关重构/格式化/依赖升级、目标是一句话而不是列表,自行继续,不必问人
   - `STOP` → **不许开 ready PR**。按 ACTION 的三问自查后,按「怎么问」用飞书把"当前行数 + 自查结论 + 建议拆成几个 PR"压到三行问 Chris,他说"就这么发"才继续
   
   判据是**非测试代码**插入行(测试与快照不计),阈值 WARN 150 / STOP 300。用总行数没有区分度:#1636 总 1071 行里 779 行是测试,实现面只有 292。2026-08-04 实测梯度:实现面 54 行的 PR 一轮 review 就合并,292 行的跑了 4 轮,450 行的振荡 8 轮后废弃重做——**规模与 review 轮数是断崖关系,不是线性**。小 PR 不振荡不是因为它更规范,而是邻域太小、bot 挖不出东西。这条闸门是控制 review 无限扩展的**入口侧**手段,和「3 轮硬上限」(过程侧)、drift-check(push 侧)是三道不同位置的锁。
2. **ready 前刷新线上基线**:再次 fetch 真正上游默认分支，检查任务开始后已合并的相关 PR/提交是否与本功能重叠。若重叠，先按仓库规则把最新默认分支合入并完成冲突/行为对齐，再做最终 self-review 和测试；禁止在旧基线上测完、发 PR 后才迁移。
3. **整理 commit 历史**:按「Commit 纪律」squash/reword，确保 reviewer 看到干净叙事。
4. push + 创建 PR；档位按上面判定。ready PR 创建成功或 draft 转 ready 后，**下一动作必须是总管登记**，不得先汇报、等待 bot、继续做其它开发或把登记留到“最后再说”。
5. 标题描述默认中文,按仓库模板填；多行 body 用 `--body-file`，提交后拉回自检。
6. 自测确认里**如实写明未测项**,不声称没跑过的验证。
7. **ready PR 原子收口清单(同一发布动作内完成，缺一 = 发布未完成):**
   - ① 发布自检:PR 呈现正常、checks 已启动、无秒红;
   - ② 立即调用宿主 `get_current_session_id`，再执行唯一登记入口:`node ~/.agents/skills/git-workflow/scripts/hb-register.mjs <owner/repo> <PR号> --owner <会话id> --branch <分支> --worktree <绝对路径> --brief <一句话>`。脚本会核对 live PR 的 state/draft/head 分支、原子写入 tracked[] 并回读。任何一步失败都要当场修复或明确报告“PR 已发布但总管登记失败”；禁止静默跳过、手拼 JSON 或假设自愈补录。
   - ③ 交付汇报**末尾固定带一行** = 登记脚本 stdout 输出的 `心跳: <schedule 名> 已含 #<N>(回读√)`,原样粘贴——汇报里没有这一行 = 收口没做完,不许结束回合。
   - ④ 会话标题改为 `#<N> <简述> · 待bot`(格式与状态字典见「收口」节;多 PR 会话追加段)。
   - draft 不建心跳,标题状态标 `draft`。bot 首批意见不守等(settle 后由心跳合并转交)。

## 收口

- **终态收口三件套（合并/关闭的当回合必须全做完,缺一视为未收口）**。2026-08-03 实踩:#1371 与 #1376 的 owner 都收到了 terminal handoff、都做了 live 复核、都移除了 tracking、还都写了 memory——**两个都漏了改标题**,于是侧栏上「🚧#1371 … · 待bot」在 PR 合并后又挂了好几个小时,用户看到的是完全过期的状态。漏项是系统性的（两个不同 harness 的 session 同时漏),不是偶发:
  1. **fetch 核对终态**:`state=MERGED/CLOSED`、merge commit;

- **会话标题全程反映 PR 号与进度(用户硬要求,2026-07-29;emoji 前缀 07-30 定稿)**:段格式 `<emoji>#<N> <简述> · <状态>`。**emoji 只有 4 个桶**(用户明确要求不超过 4 个,按"要我做什么"分,不按具体状态分):`🔴 要动手`(冲突/CI红/修review/TTL到期)> `🚧 等别人`(等放行/待人审/待合并/待bot)> `✅ 完结`(已合并/已关闭)> `📝 主动draft`;一段命中多桶取优先级最高的。具体状态词仍写在 ` · ` 后:`修review(n条) / 冲突 / CI红 / 等放行 / 待人审 / 待合并 / 待bot / draft / 已合并 / 已关闭`,可用 `+` 并列(如 `🔴…· 修review(5条)+冲突`)。多 PR 会话每 PR 一段用 ` | ` 连接、各段自带 emoji。**每次更新标题都做稳定分区:所有未完结段保持原相对顺序在前，`已合并/已关闭`段保持原相对顺序统一收束到末尾；禁止因某个终态 handoff 把已完结 PR 插到前面。**owner 在每个跃迁点主动改标题(发 PR→`🚧…· 待bot`、收到转交开始修→`🔴…· 修review`、一轮闭环推完→`🚧…· 待bot`、approve 且绿→`🚧…· 待合并`、合并→`✅…· 已合并`);sweep 每轮会按 live 状态**强制对齐**(v3s handoff 的「本 PR 标题段应为」行已带 emoji 与稳定分区规则),标题漂移会被覆盖——别跟它打架。PR 集合变化(撤回/新增)时同步更新标题与心跳配置。

核心不变量（任何时候都必须遵守,细节协议见下方指针）:

- **全局只有 1 条 sweep schedule**:`PR 总管 · gw-hb/v4 (luna)`。新仓库接入只增加一份 `sweeps/<owner>_<repo>.json` 配置，绝不按 repo/PR 新建 schedule，也不 `bindToCurrentSession`。日常 ready PR 登记只运行 `hb-register.mjs`，不需要读取完整 heartbeat 协议；只有维护总管 schedule、预检脚本或 tracking 数据结构时才读 `references/heartbeat.md`。
- **tracked[] 是机器级清单,不是会话私有的**:本机所有在飞 PR 登记在同一个文件里,每条各有各的 owner。看到其它会话的条目是常态,**不要"帮忙"清理、修改或质疑别人的条目**——只有该 PR 的 owner 才能动它的登记(2026-08-05:一个刚收口的 owner 把同机另一会话的合法登记误当"漏进来的",若当时顺手清了就是把在飞 PR 打成失联)。
- heartbeat 只侦测/转交,**禁止自己修码、push、resolve review、合并 PR**;owner 主线程才处理 PR。handoff 只送事实（固定格式见 heartbeat.md）,不送建议、不提醒纪律——纪律由 owner 自己的 skill 管。
- **找不到 owner 时只报告**：禁止接管、创建替代会话或代为处理。事实型 handoff 只投 tracked[] 登记的真实主线程。
- PR 终态/TTL 到期时的分工:**owner 负责移除 tracked 项**——走 `hb-register.mjs <owner/repo> <PR号> --remove <原因>`（收口三件套之②,脚本带锁+原子写+回读,并拒绝移除仍 OPEN 的 PR）;**总管负责清该 PR 的 pending/cache/coordinator 状态**。两边都跑过一遍不会坏（第二次会报"本来就不在 tracked 中"）。**全局 v4 schedule 常驻，tracked 为空也不得删除或 pause**。
- **人为叫停一个仍 OPEN 的 PR 用 `--pause <原因>`**（2026-08-04 新增）:`--remove` 只服务终态,`--pause` 是让 OPEN PR 停止被转交的唯一合法出口——用于 review 循环已把 PR 泵成巨物、多会话交叉工作、或方案要整体重做而需要先冻住的场合。它比 `--remove` 多写一步 `ignore[]`,因为预检的 `autoRegister` 会扫作者全量 open PR 自动补登记,只摘 `tracked[]` 会在下一轮被捡回来（还会按 `session_pr_refs` 的 `last_seen_at` 重选 owner,可能把路过的会话选成 owner）。恢复跟进 = `gh pr ready <N>` 后照常 register，脚本自动移出 `ignore[]`。**叫停不等于处置**:PR 本身仍 open，关/改/重做是产品决策，交用户裁决。
- 总管固定 `*/15`；bot 催办/nag 重复评论不算新变化。
- **bot 意见等出齐再转交**:门控内置 settle 窗口——review bot 还在陆续出意见/checks 还在跑时压住不放行,全部安静后一波合并成一条 handoff（硬阻塞事件除外）。owner 端不要绕过它去逐条轮询。
- **tracking 唯一入口 = 本地发布 PR 时的收口登记;sweep 永不扫描作者全量 open PR**(2026-07-31 用户裁决:自愈全量扫描把另一台设备发布的 PR 挖进本机跟踪,两台机器同时处理所有 PR)。其它机器/会话发布的 PR 与本机 sweep 无关;漏登记 = 失联,没有兜底,收口清单②因此是硬要求。
- sweep 使用订阅通道 `gpt-5.6-luna`，无变化由 pre-run 零 token 拦截；不得换成不可靠的低档脚本直投。
- 总管只负责等完整 review wave、一次性交付全部有效问题；不规定修复轮数，也不把普通有效问题留到下一轮。

**仅在维护总管 schedule、pre-run hook、tracking 数据结构或排障投递链时读完整协议:**
`~/.agents/skills/git-workflow/references/heartbeat.md`。普通 PR 登记不读，直接运行脚本。
